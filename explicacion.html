Unikernel ARM64 con servidor HTTP

Un programa en C que arranca directamente sobre una máquina virtual ARM64 emulada por QEMU, sin sistema operativo, responde a peticiones HTTP en el puerto 18080 y, en la ruta /remote, consulta otro servicio HTTP y devuelve su respuesta.

1. Qué es un unikernel

Un unikernel es un programa que incluye solo lo que necesita para funcionar y se ejecuta directamente sobre el hardware (o una máquina virtual) sin un sistema operativo de propósito general. Aquí no hay Linux, ni drivers genéricos, ni procesos, ni libc: el propio código inicializa el procesador, la UART (consola) y la tarjeta de red, y atiende el tráfico TCP/HTTP.

El proyecto implementa todo eso en unos pocos archivos:

  • Un driver mínimo de VirtIO-Net (tarjeta de red virtual) por MMIO, en modo legacy (versión 1).
  • Una pila de red propia: Ethernet, ARP, IPv4, TCP y un HTTP de una sola respuesta.
  • Un cliente HTTP saliente muy simple, usado solo por /remote.
  • Un bucle de polling: no usa interrupciones, consulta constantemente la cola de recepción.

2. Arquitectura general

El sistema tiene tres capas: el Mac (host), QEMU (la máquina virtual y su red de usuario) y el unikernel (el código de kernel.c) que corre dentro de esa máquina.

Petición directa

Cliente curl en el Mac → puerto 18080 del host → QEMU hostfwd → VirtIO-Net → pila TCP/IP en C → respuesta HTTP 200

Petición /remote

Cliente curl en el Mac → 18080 → QEMU → unikernel → unikernel abre TCP a 10.0.2.2:9000 → QEMU/SLIRP reenvía al Mac → servicio del Mac responde → unikernel devuelve ese cuerpo al cliente

Máquina virtual

QEMU emula la placa virt de ARM: CPU, RAM, UART PL011 y dispositivos VirtIO por MMIO. El unikernel habla con esos dispositivos escribiendo en direcciones de memoria concretas.

Red de usuario (SLIRP)

QEMU actúa como router NAT. El unikernel tiene la IP 10.0.2.15, la puerta de enlace es 10.0.2.2 (el propio Mac) y el puerto 18080 del Mac se reenvía al del unikernel.

3. Relación con QEMU

QEMU no ejecuta el sistema operativo ni la red: simula el hardware que el unikernel espera encontrar. Todo lo que el código escribe en una dirección fija llega a un dispositivo simulado por QEMU. Esta sección enlaza cada pieza del hardware simulado con el código que la usa.

Qué hace QEMU en cada paso de una petición

  1. Host → guest: curl conecta a localhost:18080 del Mac. SLIRP recibe el paquete por hostfwd, construye un frame Ethernet con destino 10.0.2.15 y lo deposita en un descriptor del anillo RX de la tarjeta virtual.
  2. Notificación: el unikernel escribe el índice de cola en QUEUE_NOTIFY y QEMU sabe que hay trabajo; el polling del unikernel ve avanzar used.idx.
  3. Respuesta: cuando tcp_tx o virtio_net_send escribe en el anillo TX y notifica a QEMU, SLIRP toma el frame, reconstruye el paquete TCP/IP y lo entrega al socket del Mac.
  4. Gateway: las consultas ARP a 10.0.2.2 las responde QEMU. Esa IP no es una máquina real: es el propio Mac visto desde la red de usuario.
Por qué 10.0.2.2:9000 llega al Mac. SLIRP reserva 10.0.2.2 como alias del host. Un unikernel que conecta a 10.0.2.2:9000 abre en realidad un socket TCP hacia el puerto 9000 del Mac. Por eso el servicio de prueba de /remote se ejecuta en el Mac, no dentro del unikernel.

Qué tiene que hacer el unikernel (y QEMU no hace)

  • Inicializar el dispositivo VirtIO: reset, handshake de estado, negociación de features y configuración de colas.
  • Construir y leer frames Ethernet, ARP, IPv4 y TCP con sus checksums. QEMU no hace de servidor TCP por el guest.
  • Mantener el estado de cada conexión TCP (secuencia, ACK, puertos).
  • Configurar el procesador: FP/SIMD, pila y BSS (ver sección 8).

Secciones de kernel.c

  1. UART PL011 (líneas 5–26): escribir un byte en 0x09000000 es enviarlo a la consola. No hace falta esperar al registro de estado.
  2. Utilidades (líneas 28–60): memcpy, memset, memcmp propias (sin libc) y htons/ntohs/htonl/ntohl, porque la red va en big-endian.
  3. VirtIO-Net (líneas 62–257): constantes de registros legacy, estructuras de virtqueue, virtio_net_init (línea 167) y virtio_net_send (línea 232).
  4. Pila de red (líneas 258–404): estructuras Ethernet/ARP/IPv4/TCP, checksum y tcp_checksum, la respuesta fija http_payload (línea 351) y send_tcp_packet (línea 362).
  5. Cliente saliente (líneas 405–690): constantes del upstream, tcp_tx genérico, envío de la respuesta por trozos, ARP, máquina de estados del cliente y outbound_rx.
  6. handle_packet (línea 601): separa ARP, segmentos del upstream y segmentos del cliente en el puerto 18080.
  7. kernel_main (línea 694): imprime el banner, inicializa la red y entra en el bucle de polling, que también gestiona el timeout del upstream.
Respuesta HTTP. El contenido está fijo en http_payload: un HTML con el texto "Unikernel ARM64 Bare-Metal" y Content-Length: 175. No hay parser de peticiones: cualquier payload recibido en el puerto 18080 recibe la misma respuesta 200 OK, salvo que empiece por GET /remote , que activa el cliente saliente.

6. Flujo de una petición directa

  1. curl http://localhost:18080 abre TCP al host; QEMU reenvía el paquete al guest.
  2. El bucle de polling detecta un nuevo elemento en rx_vq.used y llama a handle_packet.
  3. Se comprueba que el paquete es IPv4, TCP, destinado a 10.0.2.15 y al puerto 18080.
  4. SYN → se responde SYN+ACK. El cliente envía ACK y después PSH con la petición.
  5. Con datos entrantes que no son GET /remote, se envía un único segmento PSH+ACK+FIN con el HTML.
  6. Si el cliente envía FIN, se responde con ACK.
  7. El buffer RX se devuelve al anillo avail y se notifica a QEMU para la siguiente recepción.

7. Cliente saliente: GET /remote

Cuando la petición empieza por GET /remote , el unikernel actúa también como cliente HTTP: abre una conexión TCP al upstream, espera la respuesta y la reenvía al cliente original.

Estados de la conexión saliente

OUT_IDLE → OUT_ARP (si falta la MAC del gateway) → OUT_SYN → OUT_WAIT_DATA → vuelta a OUT_IDLE
PasoQué ocurreFunción
1Llega GET /remote. Se guarda la MAC, IP y puerto del cliente y se responde ACK al cliente.handle_packet
2Se incrementa el número de conexión, se elige puerto local 40000 + n e ISN 5000 + n·1000. Cada conexión usa puerto e ISN nuevos porque SLIRP conserva el estado de la anterior.outbound_start
3Si la MAC del gateway 10.0.2.2 es desconocida, se envía un ARP request y se espera la respuesta.send_arp_request
4Se envía el SYN a 10.0.2.2:9000. Al recibir SYN+ACK, se envía el ACK y la petición GET / HTTP/1.1 en el mismo segmento.outbound_send_syn, outbound_rx
5Cada segmento de datos se copia en up_buf (4096 bytes) y se confirma con ACK. Los segmentos fuera de orden se descartan confirmando lo que ya se tiene.outbound_rx
6Con FIN del upstream, se cierra el lado saliente y se envía la respuesta al cliente en trozos de 1200 bytes; el último lleva FIN.outbound_finish, send_client_response
7Si no llega respuesta en OUT_TIMEOUT_TICKS iteraciones de polling (50 000 000), se envía al cliente 504 Gateway Timeout.kernel_main

Logs esperados en la consola

[HTTP] GET /remote -> consultando upstream
[OUT] Conectando a http://10.0.2.2:9000/
[OUT] Gateway 10.0.2.2 resuelto por ARP
[OUT] Respuesta recibida: 1234 bytes -> reenviando al cliente

Si el upstream no responde aparece [OUT] Timeout esperando al upstream -> 504. El número de iteraciones de polling no equivale a un tiempo exacto; depende de la velocidad del host.

Destino fijo. La URL del upstream está escrita en el código como 10.0.2.2:9000 (IP en gw_ip, puerto en UPSTREAM_PORT, cabecera Host en upstream_req). Cambiarla a una URL externa requiere parametrizar esos tres valores y que la IP destino sea alcanzable a través de SLIRP. Ver sección 14.

8. Arranque y enlazado

  • boot.s ejecuta mrs x1, mpidr_el1 para comprobar el núcleo: solo el núcleo 0 continúa, el resto entra en wfe. La VM se lanza con un único núcleo por defecto.
  • QEMU con -kernel salta a _start en EL1. Se configura CPACR_EL1 para FP/SIMD antes de cualquier código generado por el compilador que los use.
  • La pila empieza en _start (0x40080000) y crece hacia abajo, hacia la RAM libre por debajo del código.
  • La BSS se pone a cero. Es necesario porque los anillos VirtIO y los buffers de red están ahí y deben empezar limpios.
  • linker.ld alinea rx_vq y tx_vq a 4 KiB, requisito de VirtIO legacy para QUEUE_PFN (dirección del anillo dividida entre 4096).

9. Problemas resueltos durante la puesta en marcha

El unikernel escribía [NET] VirtIO-Net encontrado y después se quedaba colgado. Se encontraron dos causas y una tercera de configuración:

a) FP/SIMD deshabilitado → Undefined Instruction

Síntoma: excepción con ESR EC=0x07 en ldr q30, [x19, #16].
Causa: -O3 genera instrucciones NEON para copiar datos, pero el núcleo no habilita el acceso a FP/SIMD. Cada instrucción trapea y el vector de excepciones (vacío) vuelve a fallar en bucle.
Solución: en boot.s, antes de llamar a C: mov x0, #(3 << 20); msr cpacr_el1, x0; isb.

b) Acceso no alineado en memoria Device → Data Abort

Síntoma: Data Abort con DFSC 0x21 (alignment fault) al escribir en 0x4008d104 con stur q31.
Causa: sin MMU activa, QEMU trata la memoria como Device-nGnRnE, donde todo acceso no alineado a su tamaño falla. El compilador genera esos accesos al copiar estructuras empaquetadas de la pila de red.
Solución: -mstrict-align en la compilación de kernel.c.

c) Puerto 80 → 18080

El filtro TCP en kernel.c, el mensaje de arranque y el hostfwd de QEMU usan el puerto 18080. En el script, hostfwd=tcp::18080-:18080 reenvía el mismo puerto del Mac al guest.

11. Ejecución: hypervisor (hvf) vs TCG

QEMU puede ejecutar el código ARM64 de dos formas. La diferencia afecta al rendimiento y a la depuración, pero no al código del unikernel.

Hypervisor.framework (-accel hvf)

Usa el hypervisor nativo de macOS. Las instrucciones del guest se ejecutan directamente en el procesador del Mac, sin traducir nada.

  • Rápido en cómputo puro, cercano a velocidad nativa. En este servidor, sin embargo, no fue más rápido que TCG (ver sección 15).
  • Requiere un Mac con Apple Silicon (arm64) para ejecutar un guest arm64.
  • Se usa con -cpu host para exponer el procesador real.
  • Es el modo que elige el script cuando uname -m devuelve arm64.
  • En esta sesión no pude trazar excepciones con este modo: -d int no mostró nada útil. Por eso la depuración se hizo con TCG.

TCG (-accel tcg, por defecto)

TCG (Tiny Code Generator) es el emulador de software de QEMU: traduce las instrucciones ARM64 a código para el host y las ejecuta.

  • Funciona en cualquier Mac, incluidos los Intel, y en cualquier host.
  • Más lento en cómputo puro. En este servidor, en cambio, fue algo más rápido que hvf (ver sección 15).
  • Permite -d int,guest_errors, que muestra cada excepción con su ESR, FAR y ELR. Es la forma de encontrar fallos como los de la sección 9.
  • El script usa -cpu cortex-a72 en este caso.

Comando equivalente en cada modo

# Apple Silicon: hypervisor nativo
qemu-system-aarch64 -M virt -cpu host -accel hvf -m 128M \
  -global virtio-mmio.force-legacy=on \
  -netdev user,id=net0,hostfwd=tcp::18080-:18080 \
  -device virtio-net-device,netdev=net0 \
  -kernel unikernel_http.elf -nographic

# Cualquier Mac: emulación TCG (y trazas de excepciones)
qemu-system-aarch64 -M virt -cpu cortex-a72 -accel tcg -m 128M \
  -global virtio-mmio.force-legacy=on \
  -netdev user,id=net0,hostfwd=tcp::18080-:18080 \
  -device virtio-net-device,netdev=net0 \
  -kernel unikernel_http.elf -nographic -d int,guest_errors -D trace.log

12. Cómo ejecutarlo y probarlo

  1. Abre Terminal.app (o Warp si no te da problemas con SSH) y ve al proyecto: 
    cd ~/unikernel/unikernel_arm64_http
  2. Ejecuta el script. Compila, enlaza y arranca QEMU en primer plano: 
    ./build_and_run.sh
  3. En otra terminal prueba la respuesta directa: 
    curl -i http://localhost:18080
    Debes ver HTTP/1.1 200 OK y el HTML con el texto "Unikernel ARM64 Bare-Metal".
  4. Para probar /remote, arranca primero un servicio en el Mac en el puerto 9000 (QEMU lo alcanza como 10.0.2.2:9000): 
    python3 -m http.server 9000 --bind 127.0.0.1
    Después, en otra terminal: 
    curl -i http://localhost:18080/remote
    Debes recibir el listado de ficheros del directorio donde arrancaste el servidor de Python.
  5. Para salir de QEMU: Ctrl+A y luego X.

Si QEMU se ejecuta en segundo plano (como en la prueba de esta sesión), se detiene con:

pkill -f qemu-system-aarch64

Lo que muestra la consola

14. Pendiente

URL externa para /remote. Hoy el cliente saliente solo consulta 10.0.2.2:9000, es decir, un servicio del Mac. El objetivo es que el unikernel consulte una URL externa y devuelva su contenido en localhost:18080. Para hacerlo hay que:
  • Elegir la URL. Solo puede ser HTTP plano: no hay TLS en el código.
  • Pasar la IP pública del destino: el unikernel no tiene DNS, así que un nombre de host hay que resolverlo antes y fijar la IP.
  • Parametrizar IP, puerto, ruta y cabecera Host en lugar de tenerlos fijos en kernel.c.

15. Rendimiento medido

Medido con wrk (brew install wrk) contra http://localhost:18080, con el mismo binario en ambos modos. Cada respuesta ocupa 175 bytes de cuerpo, unos 261 bytes con cabeceras.

PruebaTCGhvf

4 conexiones, 5 s: req/s3.1982.193

Lectura de los datos. En este servidor TCG resultó entre un 20 % y un 45 % más rápido que hvf, contra lo que cabría esperar, porque hvf ejecuta el código directamente en el procesador. La hipótesis es que el cuello de botella no es la CPU, sino los accesos MMIO de VirtIO y el bucle de polling: en hvf cada acceso obliga a salir al hypervisor, mientras que TCG lo resuelve dentro del emulador. Esta hipótesis no está comprobada; para verificarla haría falta contar los accesos MMIO por petición.
Qué mide y qué no. La cifra incluye el loopback, el NAT de SLIRP de QEMU y el propio cliente wrk en el Mac, no solo el unikernel. Por eso la latencia de ~0,4 ms es mayor de lo que cabría esperar de un código tan simple. Los errores de socket con 4 conexiones varían entre ejecuciones y no son un dato fiable para comparar.
Por qué no usar ab. ab reporta 19.936 req/s, pero es un resultado falso: cada petición tiene 0 bytes de respuesta y Write errors: 5. La pila TCP del unikernel no acepta el formato de petición que envía ab. curl y wrk sí obtienen 200 OK.

Comandos usados

# Una conexión, 10 segundos, con distribución de latencias
wrk -t1 -c1 -d10s --latency http://localhost:18080

# Cuatro conexiones, 5 segundos
wrk -t1 -c4 -d5s --latency http://localhost:18080

16. Limitaciones

  • La red es un ejemplo didáctico: no implementa retransmisiones, ventanas TCP reales ni control de estado completo. Cada conexión saliente de /remote es única y sin reintentos.
  • El servidor sirve una sola respuesta fija; no hay parser HTTP ni rutas, salvo el disparador GET /remote.
  • El cliente saliente solo habla HTTP/1.1 plano, sin TLS, sin DNS y sin seguir redirecciones.
  • Todo el código corre en EL1 sin MMU; por eso la memoria se trata como Device y el alineamiento importa.
